\## 3. Описание реализации



Умножение матриц — это три вложенных цикла. Параллелить удобнее всего

самый внешний цикл по строкам: каждая строка результата считается

независимо от других, поэтому потоки не мешают друг другу.



Ключевая строчка в коде:



```cpp

\#pragma omp parallel for schedule(static)

for (int i = 0; i < n; i++)

&#x20;   for (int k = 0; k < n; k++) {

&#x20;       double aik = A\[i]\[k];

&#x20;       for (int j = 0; j < n; j++)

&#x20;           C\[i]\[j] += aik \* B\[k]\[j];

&#x20;   }

```



Число потоков задаётся переменной окружения `OMP\_NUM\_THREADS`

перед запуском программы.

\## 8. Выводы



\*\*Корректность.\*\* Сравнила с NumPy — расхождения только в пределах

погрешности. Значит, распараллеливание ничего не сломало.



\*\*Мелкие матрицы (200, 400).\*\* Параллелить их почти нет смысла.

На N=200 с 4 потоками вышло даже медленнее, чем с одним (0.007

против 0.004 с). Накладные расходы на потоки больше самой работы.



\*\*Средние и крупные (1200, 1600).\*\* Тут OpenMP себя оправдывает.

На N=1200 с 8 потоками — почти в 5 раз быстрее одного

(1.33 → 0.26 с).



\*\*Странность на N=2000.\*\* С 8 потоками вышло хуже, чем с 4

(3.15 против 2.39 с). Причина — гибридный i5-12450H: 4 быстрых

ядра и 4 медленных. На 4 потоках работают только быстрые, на 8 —

подключаются медленные, и всё замедляется.



\*\*Оптимальное число потоков.\*\* Для моего ноутбука — 4, по числу

быстрых ядер. Больше не помогает.



\*\*GFLOPS.\*\* Растёт с размером и числом потоков, но не бесконечно:

все потоки читают одни и те же данные, и упирается в память

(memory-bound задача).



\*\*Итог.\*\* OpenMP ускоряет умножение матриц, но не всегда одинаково

хорошо. На мелких матрицах эффекта нет, на крупных — есть, а на

гибридных процессорах лучше ставить потоков по числу быстрых ядер.
